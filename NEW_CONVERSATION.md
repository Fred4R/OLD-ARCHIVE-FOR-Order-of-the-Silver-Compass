## Story and repository synergy

Repository work may echo symbolically in fiction, but the technical action and fictional event are never identical.

Use the action's **function** as the symbol.

Examples:
- exact-source retrieval -> sealed original dispatch;
- checksum -> matching seal or serial impression;
- authority routing -> jurisdictional seal or steward's ledger;
- crosswalk -> compass bearing or indexed chart;
- validation -> muster check or cogitator green-mark;
- unresolved information -> open docket, unfilled seal-space or unspent token;
- current-rules amendment -> newly dated tactical order;
- preserved roster snapshot -> archived muster roll;
- failed retrieval route -> blocked archive door or failed signal path.

Use symbolism only when it serves the scene.

Never make GitHub, validators, files or AI tooling literal in-world facts.

## Human-evidence and identification routing

For personal identification work, use the original methodology PDFs under `Sources/Methodology/`.

Route by function:

- Kyllonen & Zu (2025): constructs, measurement, validity, reliability and method effects.
- Connelly & McAbee (2024): self/other differences, reputation, person perception, context and accuracy.
- Roberts & Yoon (2022): traits, motives/goals, skills/abilities, narrative identity, development and person-situation interaction.

These sources improve inference.

They do not diagnose Fred, create Silver Compass canon, establish Warhammer lore/rules, or dictate fictional outcomes.

For substantial identification:
- distinguish behavior, state, trait/disposition, motive/goal, value, skill/ability, self-concept/identity, reputation, narrative identity and interpretation;
- compare the strongest candidate, strongest alternative and a superficially similar deeper mismatch;
- calibrate confidence;
- state what evidence could change the result.

## Repository work procedure

For meaningful repository changes:

1. create a branch from current `main`;
2. make the smallest useful change;
3. update authority/source/navigation records only when the change requires them;
4. update `SHA256SUMS.txt`;
5. open a pull request;
6. require the repository validator to pass in GitHub Actions;
7. merge only the tested tree;
8. verify the post-merge `main` tree and automatic validator run.

Run locally when available:

`python scripts/validate_repository.py`

A passing validator proves structural consistency only.

It does not prove truth, canon acceptance, current whole-list legality or resolution of an unresolved question.
